## Veredito: **APROVADO COM RESSALVAS**

Nenhum bloqueante. O PR melhora a postura de privacidade em relação ao que está na `main`: antes o contador de rate limit vivia só em memória por instância; agora é compartilhado, com prazo, e a chave no Redis é derivada do IP em vez de ser o IP. Não há dado novo coletado, não há finalidade nova, e o tratamento de IP para segurança já está registrado em `bases-legais-e-consentimento.md` (linha "Logs de segurança e auditoria", art. 7º, II com Marco Civil art. 15, e art. 7º, IX). Por isso o item 1 do checklist é "Sim" e não há o que vetar.

Dito isso, a descrição do PR afirma que "a chave guarda só hash do IP", e essa afirmação é falsa em dois pontos concretos (R1 e R2). Ela não é apenas imprecisão de texto: é a frase que entraria no ROPA e no RIPD como medida de mitigação. Mitigação descrita e não implementada é pior que mitigação ausente, porque desliga a atenção de quem revisa depois. As duas correções são pequenas e estão especificadas abaixo.

### Pontos fortes

- O `FallbackRateLimitStore` resolve o problema certo: Redis fora não derruba requisição, e a proteção degrada para o limite por instância em vez de desaparecer. O cooldown de 5 s evita pagar o timeout em toda requisição, e a volta do Redis é registrada em log.
- `enableOfflineQueue: false` com `maxRetriesPerRequest: 0` e `commandTimeout: 100` é a configuração correta para falhar rápido. O listener vazio de `error` evita o ruído de "Unhandled error event" do ioredis — e, melhor, evita que esse ruído carregue string de conexão para o log.
- O script Lua faz `INCR` e `PEXPIRE` de forma atômica e recoloca o prazo se a chave aparecer sem TTL. Sem isso, uma chave órfã viraria bloqueio permanente de um IP. Bom cuidado.
- `RATE_LIMIT_EXEMPT_PATHS` tira as sondas de saúde do limite, com justificativa escrita no comentário. Sem isso, um 429 em `/health` tiraria instância saudável de serviço.
- `safeErrorHandler` para os body-parsers fecha um vazamento real de detalhe interno: sem ele, a API ecoava a mensagem do parser ("Expected double-quoted property name in JSON at position 13").
- `noStore` em todas as respostas, CSP `default-src 'none'`, CORS por allowlist exata com erro no boot se alguém puser curinga. Nada a acrescentar.
- O job de segurança sobe Redis e **falha** em vez de pular quando o Redis não está disponível. Teste que pula é verde falso; esse não pula.

## 2. Ressalvas

### R1 (alta) — SHA-256 sem segredo sobre IPv4 é reversível em segundos

`apps/api/src/security/rate-limit-store.ts`:

```ts
export function rateLimitKey(clientId: string): string {
  return `rl:v1:${createHash('sha256').update(clientId).digest('hex').slice(0, 32)}`;
}
```

O comentário acima dela é honesto e admite o problema: "O hash não é segredo forte (o espaço de IPv4 é pequeno)". Ele é mais que não-forte: o espaço do IPv4 tem 2³² endereços, e uma tabela completa de SHA-256 truncado em 32 hex se constrói em minutos num laptop. Quem obtiver as chaves do Redis (dump, réplica, log de comando lento, acesso de leitura) recupera o IP exato. Para efeito de LGPD, hash sem chave sobre espaço enumerável continua sendo dado pessoal, e a medida não conta como pseudonimização defensável.

O ponto importante é que **isso não torna o PR ilegal**: guardar o IP em claro para fins de segurança já é lícito pelo art. 7º, II (com o art. 15 do Marco Civil) e pelo art. 7º, IX. O defeito é o PR afirmar uma proteção que não entrega. Ou se entrega a proteção, ou se corrige a afirmação.

Correção pedida (barata, uma linha de lógica):

```ts
import { createHmac } from 'node:crypto';

/**
 * IP é dado pessoal. A chave leva HMAC-SHA256 com segredo do gerenciador de segredos:
 * sem a chave, o espaço enumerável do IPv4 não permite reverter o identificador.
 */
export function rateLimitKey(clientId: string, secret: string): string {
  return `rl:v1:${createHmac('sha256', secret).update(clientId).digest('hex').slice(0, 32)}`;
}
```

Com `RATE_LIMIT_HASH_KEY` vindo do gerenciador de segredos, rotação documentada (a rotação só invalida contadores de uma janela, então é indolor), e **erro no boot em produção** se a variável faltar. Prazo pedido: antes do primeiro ambiente que receba tráfego externo real, não depois. Se a engenharia preferir não implementar agora, então a frase "a chave guarda só hash do IP" sai da descrição do PR e do ROPA, e entra "a chave guarda hash sem segredo, reversível; proteção efetiva pendente", para que ninguém decida com base na frase errada.

### R2 (alta) — O caminho em memória guarda o IP em claro, e ele é o caminho padrão

Este é o achado mais concreto da revisão. `rateLimitKey` é chamada **somente** dentro de `RedisRateLimitStore.hit`. O `MemoryRateLimitStore` recebe a mesma `key` crua e a usa direto:

```ts
const count = (this.hits.get(key) ?? 0) + 1;
this.hits.set(key, count);
```

E a `key` que chega ali vem de `http-security.ts`:

```ts
const key = req.ip ?? req.socket.remoteAddress ?? 'desconhecido';
```

Ou seja: o IP em claro, como chave de um `Map` no heap do processo. E não é um caminho de exceção — é o caminho padrão em três situações: (a) sem `REDIS_URL`, que é local e teste; (b) **em produção sem `REDIS_URL`**, onde hoje só há um `warn` (ver R3); (c) **no fallback de produção**, durante toda indisponibilidade do Redis, que é exatamente o momento em que alguém vai coletar heap dump para investigar. Qualquer snapshot de heap, core dump, ou integração de APM que capture objetos expõe a lista de IPs dos usuários ativos.

Correção pedida: derivar a chave numa só camada, a mais externa, para que todo armazenamento receba o identificador já derivado. O mais simples é o `rateLimiter` de `http-security.ts` passar a chave já derivada e os dois stores guardarem só o que recebem — com isso `RedisRateLimitStore.hit` deixa de chamar `rateLimitKey` e passa a prefixar `rl:v1:` apenas. Alternativa equivalente: aplicar a derivação também no `MemoryRateLimitStore`. O que não pode continuar é a assimetria: a afirmação do PR vale para um store e não para o outro, e o store que não cumpre é justamente o fallback.

### R3 (alta) — `REDIS_URL` ausente em produção só emite aviso

```ts
if (!url) {
  if (env.NODE_ENV === 'production') {
    new Logger('rate-limit').warn('REDIS_URL ausente em produção: rate limit só por instância');
  }
  return new MemoryRateLimitStore();
}
```

O aviso vai para o log e ninguém lê log de boot no dia em que tudo subiu. O efeito prático é um controle de segurança silenciosamente degradado: com N instâncias, o limite efetivo passa a ser N × `RATE_LIMIT_MAX`, e a API fica N vezes mais fácil de raspar. Pedido: em `NODE_ENV=production`, **erro no boot**. Falha visível na hora do deploy é mais barata que degradação invisível em produção. Se houver cenário legítimo de produção sem Redis, que ele seja explícito (`RATE_LIMIT_ALLOW_SINGLE_INSTANCE=1`) e apareça no `/health`.

### R4 (média) — O rate limit falha aberto sem deixar sinal

Em `http-security.ts`:

```ts
store.hit(key, windowMs).then(
  ({ count, resetMs }) => { /* ... */ },
  () => next(),
);
```

A escolha de deixar passar quando o contador falha é defensável: um erro de contador não deve derrubar a API. O problema é que ela é silenciosa. Com o `FallbackRateLimitStore` em uso, o `MemoryRateLimitStore` não lança, então o caminho só é alcançado em cenário imprevisto — e é justamente nesse cenário que ninguém vai saber que a proteção parou. Pedido: logar em nível de erro e incrementar métrica nesse ramo, com alerta ligado. Mais importante que o log: `/health/ready` deve informar o modo em que o rate limit está operando (compartilhado, fallback, ou desligado), para que o monitoramento veja a degradação.

### R5 (média) — `trustProxyHops` é um botão de dois gumes e não tem teste

`if (config.trustProxyHops > 0) expressApp.set('trust proxy', config.trustProxyHops);`

O número precisa casar exatamente com a cadeia real de proxies em produção. Errado para baixo (0 atrás de um ALB), `req.ip` passa a ser o IP do balanceador: todos os clientes compartilham uma chave, um único usuário esgota o limite global e nega serviço a todas as clínicas. Errado para cima, o cliente injeta `X-Forwarded-For` e escolhe a própria chave, burlando o limite por completo e podendo poluir o Redis com chaves arbitrárias. O PR não traz teste nem verificação de ambiente para isso.

Pedido: teste no job de segurança que, com `trustProxyHops` configurado como em produção, prove as duas coisas — que um `X-Forwarded-For` forjado além do número de hops **não** muda a chave, e que dois clientes distintos atrás do proxy recebem chaves distintas. E uma verificação no boot comparando `trustProxyHops` com a topologia declarada pela aba DevOps.

### R6 (média) — ROPA: a linha do contador de rate limit

O tratamento de IP para log de segurança está registrado, mas o contador de rate limit é uma operação com prazo e finalidade próprios, e precisa de linha própria para que o ROPA descreva o que de fato existe. Entra nesta rodada, em `bases-legais-e-consentimento.md`, por minha conta (é caminho meu; a engenharia não precisa tocar):

| Fluxo | Dados | Base legal | Prazo | Observação |
|---|---|---|---|---|
| Contador de rate limit | Identificador derivado do IP do cliente (hoje hash sem segredo — ver R1), contagem na janela | Art. 7º, II (Marco Civil art. 15) e art. 7º, IX — segurança e prevenção a abuso | TTL igual à janela (`RATE_LIMIT_WINDOW_MS`); nenhuma persistência além dela | Nunca associado a usuário, paciente ou tenant. Não entra em relatório, exportação ou analytics. |

### R7 (menor, fora do meu escopo — para o Revisor de Código)

`MemoryRateLimitStore` usa uma `windowStart` global para todas as chaves, não uma janela por chave. Quem chega pouco antes do reset tem uma janela curta e recebe um `RateLimit-Reset` quase expirado. Não é questão de privacidade e não muda o veredito; registro porque o comportamento difere do caminho Redis, onde cada chave tem o próprio TTL, e porque o fallback deveria se comportar como o primário.

## 3. Resumo para o sócio

Pode fazer o merge do #30 depois de **R2** (IP em claro no store de memória) e **R3** (erro no boot sem Redis em produção) — são poucas linhas e fecham o vão entre o que o PR diz e o que ele faz. **R1** (HMAC com segredo) pode entrar em PR seguinte, mas antes de qualquer ambiente com tráfego externo real; até lá, a descrição do PR precisa deixar de afirmar que o IP não é recuperável. **R5** depende de combinar a topologia com a aba DevOps.

Nada aqui impede o merge dos itens (a), (b) e (d) do PR — build do `packages/shared`, 25006 para 503 e o rascunho do bug do postgres.js. Se for conveniente separar, o rate limit pode sair em PR próprio e os outros três entram na hora.
